  • Parts B and C (the accelerator and the SoC) are a hypothetical design for teaching: they do not describe any real product. The fields, sizes and latencies are all examples chosen for the sake of explanation.
  • System assumptions: the image is split into two regions at build time: a pinned region that is never compressed, and a compressible region. C. The whole SoC

9. System architecture

This hypothetical SoC has only four kinds of components that access DRAM: the CPU, the LZ4 accelerator, one HRT client (the display), and the DRAM controller they share.

How the figures in this part are drawn: blocks with hatching are compressed data; blocks without hatching are uncompressed data. Color shows the kind of content: green is RO, blue is RW, red is pinned and HRT.

The design problem: from 1 GiB down to 512 MiB

If this SoC's software is not compressed at all, it needs 672 MiB at peak. Common DRAM part capacities come in steps like 512 MiB and 1 GiB; 512 MiB does not fit, so you have to buy 1 GiB, and the extra 350 MiB sits idle most of the time. The goal of this section is to use DRAM compression to fit the same software into 512 MiB, with about 10% margin left over.

ItemContentsSize
Pinned imageKernel core, interrupt handlers, pager, LZ4 driver, HRT code and data34 MiB
Pinned run-time dataKernel heap, page tables, DMA buffers, queues22 MiB
HRT carve-outThe display's 3 frame buffers at 1920×1080, about 24 MiB, plus other HRT buffers36 MiB
ROOrdinary code and constants248 MiB
RW .dataInitialized data26 MiB
RW heap, stackAt peak306 MiB
TotalNeeded without compression672 MiB

Pinned and HRT together are 92 MiB that cannot be compressed, so the remaining 580 MiB of content, plus the COT, has to fit into 512 - 92 = 420 MiB, with margin to spare. Whether this is achievable depends on two things: how much of the data is cold, and how good the compression ratio is. The following explains, in order, how the image is split, hot and cold data, how the size of each region is decided, and finally checks under what conditions this scheme fails.

How the image is split into two regions

This document assumes the SoC has no storage device it can read back from at any time: the image is read from flash once at boot, and after that everything must stay in DRAM. So even code has to be compressed, or no space is saved. At build time, the linker places each section into one of two VA ranges:

RegionContentsUncompressed sizeWhere it lives after boot
PinnedKernel core, interrupt handlers, pager, LZ4 driver, HRT code and data34 MiBThe pinned region, always present
Compressible, read-only (RO)Normal code, constants248 MiBCompressed at build time, loaded straight into the pool at boot
Compressible, writable (RW)Initialized data (.data)26 MiBLoaded uncompressed into the frame cache at boot
Compressible, writable (RW).bss, heap, stackup to 306 MiBA frame is allocated and zero-filled only when first used

The pager and the LZ4 driver must be in the pinned region: if the code that handles page faults were itself compressed, it could never be decompressed again. HRT code and data are here too, because they cannot wait for decompression.

.data could also be compressed offline. Its initial values are fixed at build time, so the build tool could compress it just like RO and it could go straight into the pool at boot. The only difference from RO is that .data gets written: the compressed copy is valid only while the page has not been modified, so it has to be released after the first decompression, and the page is handled as RW from then on. In this document .data is only 26 MiB and is used soon after boot, so it is loaded uncompressed. This choice affects how much DRAM is in use right after boot, but not how much DRAM is needed at peak.

The compressible range is the 580 MiB starting at VA 0x7F12_2000_0000: the first 332 MiB are RW (.data 26 MiB, plus heap and stack 306 MiB), the last 248 MiB are RO. The handle is simply the number of the page within this range, so the COT has 580 MiB ÷ 4 KB = 148,480 entries, about 4.5 MiB, allocated as 5 MiB (Section 10).

Hot data and cold data: compression only helps for cold data

To know how much can be saved, first separate hot from cold:

  • Hot page: used often recently. It must sit uncompressed in the frame cache, because the CPU can only read and write uncompressed data. If it were compressed, every use would take a page fault followed by a decompression, several µs each time (Section 13), and the system would be too slow to use.
  • Cold page: not used for a long time. It can be compressed and kept only in the pool, where it takes less space; only when it is actually used again is the cost of one decompression paid.

How the kernel knows which is which: every time the CPU accesses a page, the CPU MMU sets an accessed bit in its PTE. The kernel periodically scans and clears these bits; a page whose bit has not been set again for a while is cold. So “cold” is not a fixed property of a page: the same page moves back and forth between hot and cold with the behavior of the program.

The hot-to-cold ratio is a property of the workload, not a parameter you can set. So the first step of the design is measurement: under the most demanding scenario, count how many pages have their accessed bit set over a period of time; that is the hot data. Then compress the memory contents page by page with LZ4 to get the compression ratio (this is what the Lab in Section 5 does). This document assumes the measurements come out as follows:

MeasurementAssumed result
Hot RO30 MiB, 12% of RO
Hot RW (at peak)80 MiB, 24% of RW
RO compression ratio55%, including rounding up to 512B chunks
RW compression ratio45%, assuming the heap often holds large runs of zeros and sparse data, which compress better than code

These four numbers are assumptions of this document, not measurements from any real system. In a real design, replace them with your own measurements; the last subsection looks at whether the scheme still holds when they get worse.

How the region sizes are decided

  1. The parts that cannot be compressed are allocated at full size: pinned 56 MiB (image 34 + run time 22), HRT 36 MiB.
  2. COT: 148,480 entries × 32 B ≈ 4.5 MiB, allocated as 5 MiB.
  3. The frame cache must hold the hot data: 30 + 80 = 110 MiB, plus a margin of about 27%, allocated as 140 MiB, that is 35,840 frames.
  4. The pool must hold all RO objects and the cold RW: 248 × 0.55 = 136.4 MiB, plus (332 - 80) × 0.45 = 113.4 MiB, 249.8 MiB in total; with a 10% margin, allocated as 275 MiB.
  5. Total: 56 + 36 + 5 + 275 + 140 = 512 MiB.

Why the margin is split between two places: the 30 MiB in the frame cache is for when the hot data grows; if it runs out, the system thrashes. The 25.2 MiB in the pool is for when the compression ratio gets worse or the cold data grows; if it runs out, the result is POOL_FULL. Both are fixed regions laid out at boot time, and the margin on one side cannot be lent to the other, so each side needs its own.

What happens at build time and at boot time

  1. At build time: the tool compresses each RO page with LZ4 on its own, lays them out in order as one contiguous chunk image, and generates the COT entries for these pages. A page that does not compress (more than 3584 B) is stored uncompressed in 8 chunks instead, and its COT entry is marked RAW.
  2. The boot loader partitions DRAM: it lays out the regions as in the table above.
  3. Load the image: the pinned part is copied to the pinned region. The RO chunk image is copied to the start of the pool; it was laid out for this position at build time, so the chunk numbers need no change. The RO COT entries are written to their positions in the COT. .data is copied to the frame cache and valid PTEs are set up for it.
  4. Set up the accelerator: write the COT base and the pool base, then issue the initialization command, which builds all chunks after the RO image into the free-chunk stack (Section 10).
  5. Start running: the PTEs of RO pages all start out invalid; the first use of a page takes a page fault and decompresses it into the frame cache.

Below, these 5 steps are broken down to show step by step what the build tool produces, what goes into flash, and what the boot loader and the INIT command of the accelerator each write. The example uses one RO page: VA 0x7F12_3A3F_1000, handle 0x1A3F1, the same page as in the third flow of Section 12. RO pages hold code, and this page has no code sample, so the samples from Section 5 stand in as contents: the first 4 RO pages use the four samples text, pointer array, random and all zeros, in that order, and 0x1A3F1 holds the first 3271 bytes of the text sample followed by zeros; the compressed sizes and checksums are what the LZ4 code running on this page actually computes. The other 63,483 pages are not given individual contents; only their total of 136.4 MiB is used. Rows with a blue background in the table are what this step changes.

    First, keep page and frame apart: RO page and RW page refer to contents: a 4 KB piece of data, named by its VA, whose kind is decided at build time. A frame in the frame cache refers to a location: a 4 KB slot of DRAM, named by its PA, laid out at boot time. Pages move back and forth between frames and the pool; a frame stays where it is, only the page inside it changes. For example, in Section 12, RW page H1 lives in turn in frame F0, in 4 chunks of the pool, and in frame F3; frame F0 in turn holds D, H1, R1 and R4. The figures below use color for contents (green RO, blue RW) and the block it sits in for location: blue in the frame cache is an uncompressed RW page, blue in the pool is a compressed RW page.

    “Empty” also needs care. An empty frame is a DRAM location that currently has no page in it; it occupies DRAM, and it holds stale data left by its previous user. An untouched page is a piece of contents that is not stored anywhere yet; it is logically all zeros but occupies no DRAM at all. When the two first meet, the kernel takes an empty frame, zero-fills it, and maps the page to it; decompression needs no clearing first, because it overwrites all 4096 bytes. Separately, a page whose contents are all zeros (such as R3 in Section 12) is a real page and still takes space: 4 KB in a frame, 26 bytes compressed, but still one 512B chunk.

    RO objects stay in the pool from boot onward, so evicting an RO page from the frame cache only takes invalidating the PTE and dropping the frame; no recompression is needed. An RW page, by contrast, is compressed when evicted, and its object is released after it is faulted back in.

If the RO object were released after decompression instead, these 16.5 MiB could also be saved, but every RO page eviction would have to recompress. Here the hot RO is only 30 MiB, so the cost is small; the copy is kept, and in exchange evicting an RO page only has to drop the frame.

    How the pool is split into RO, RW and Free

    In the pool only the RO size is fixed; RW and Free share the remaining space:

    • RO: fixed at boot time, unchanged afterwards. Its size is the sum of the chunks each RO page needs after compression, and the build tool can compute the exact value; in the example it is about 136.4 MiB, roughly 279,000 chunks. They occupy contiguous positions at the start of the pool, and because RO objects are never released, this segment never develops holes.
    • RW and Free: share the remaining 138.6 MiB with no fixed boundary. When an RW page is compressed, chunks are taken from Free; when it is faulted back in, the chunks are returned to Free. So the chunks of the two are interleaved, which is why Section 10 manages free chunks with a stack.
    Point in timeRORWFree
    Just after boot136.4 MiB0138.6 MiB
    Normal running136.4 MiBchanges constantly138.6 MiB minus RW
    RW peak136.4 MiB113.4 MiB25.2 MiB, the pool margin

    Does RW need an upper limit: no, because RW and Free are the same space to begin with. The kernel can, however, set a low-water mark: when Free drops below a certain amount, eviction prefers dropping frames of RO pages and stops trying to compress RW. This avoids discovering halfway through a compression that the pool is short and wasting the job. An incompressible RW page also temporarily occupies up to 7 chunks before it fails, so the low-water mark must leave at least that many.

    All the numbers above rest on assumed measurements. The table below makes one of them worse, keeps the rest unchanged, and checks whether the demand of either region exceeds its allocation (frame cache 140 MiB, pool 275 MiB):

    So this scheme tolerates about 25% more hot data, but it is sensitive to the RW compression ratio: going from 45% to 55% uses up the pool headroom. There are three ways to make it more robust:

    • Measure more accurately: compression ratios and hot data must be measured under the tightest real scenario, not as averages.
    • Let the two regions borrow margin from each other: when the third row of the table above fails, the pool still has 43 MiB free. If the pool were not a fixed carve-out but allocated dynamically from the same DRAM in units of, say, 2 MiB, the boundary between frame cache and pool could move as conditions change. The cost is an extra level of pool segment table in the LZ4 MMU, making both hardware and software more complex.
    • A fallback for when memory really runs out: first drop frames of RO pages, then limit the memory use of background work, and only then terminate programs. These policies must be decided at design time.

    10. Two MMUs

    Section 9 mentions that the accelerator has its own MMU. This section starts from zero with the problem it has to solve, and only compares it with the CPU MMU at the end.

    One clarification first: the LZ4 specification does not define any MMU. The LZ4 MMU, the COT and the CTLB are all designs and names of the hypothetical SoC in this document. Real products may have similar functions, but the names and details differ.

    The problem: the compressed size is different every time

    Suppose a 4KB page compresses to 2296 bytes and has to be stored in the pool. The most direct approach is to find a contiguous free region and put it there, but the next object may be 3200 bytes, and the one after that 26 bytes. After objects are stored and deleted over and over, the free space is cut into small pieces, and the situation in the top half of the figure below appears: the total free space is enough, but the object does not fit.

    So this document cuts the pool into fixed 512B chunks; when the data does not fit in one chunk, another one is taken. The cost is that the pieces of one object are scattered, so there has to be a place that records where they are.

    COT: the table that records where objects are stored

    An object is one compressed page. The COT (Compressed Object Table) is an array in DRAM with 32 bytes per entry, one fixed entry per compressible page, recording the compressed length, how many chunks are used, and the number of each chunk. When the page currently has no compressed object, the valid flag of its entry is 0.

    The handle is the number of the page within the compressible range, and also the index into this array: handle = (VA - 0x7F12_2000_0000) ÷ 4096. When the CPU touches a page whose PTE is invalid, the kernel does not need to record the handle separately: it computes it directly from the faulting VA and passes it to the accelerator, which uses it to look up the COT. This is the point where the CPU and the accelerator meet. The page in the example is at VA 0x7F12_3456_7000; its handle is 0x1456_7000 ÷ 0x1000 = 0x14567, which falls in the RW segment.

    Address translation: why it is called an MMU

    The decoder only wants to read the compressed data sequentially; it should not have to deal with things like “after reading 512 bytes, which address comes next”, so it only asks: where is byte 1100 of object 0x14567? Turning this contiguous position into an actual PA is address translation, which is why this document calls it an MMU:

    Translation calculator (object 0x14567, 2296 bytes in total)

    How to find empty chunks

    The LZ4 MMU manages empty chunks with a stack, that is, a pile of available chunk numbers: during compression, every time the output fills 512B it pops the top one; when an object is freed, its numbers are pushed back. Wherever a chunk is, popping one takes a single step, and no data has to be moved.

    A 275 MiB pool has 563,200 chunks; at 3 bytes per number, the full list is about 1.6 MiB, which does not fit on the chip. So this document stores the stack in two parts:

    • The top part lives in the SRAM of the LZ4 MMU: at most 512 numbers, 1.5 KB in total. Pops and returns only touch this part, so they never wait for DRAM.
    • The rest is stored in empty chunks in the pool: such a chunk is called a list chunk. Its first 3 bytes hold the number of the next list chunk, followed by the numbers of 169 empty chunks, 510 bytes in total. List chunks are linked one after another, and the number of the first one is kept in the accelerator register LIST_HEAD.
    • “No next” is represented by 0xFFFFFF: 3 bytes hold 24 bits, but the numbers of the 563,200 chunks only use 0x000000 to 0x0897FF, so anything from 0x089800 up is not a legal number, and this document picks 0xFFFFFF. 0 cannot be used, because chunk 0 is a real chunk. The next of the last list chunk is 0xFFFFFF; when there is no list chunk at all, LIST_HEAD is also 0xFFFFFF. If a refill reads a value at or above 0x089800 that is not 0xFFFFFF, the list is corrupt, and the accelerator stops and reports an error.

    When numbers move between the two parts:

    • Refill: when the SRAM has fewer than 64 numbers, read the chunk that LIST_HEAD points to, put its 169 numbers into the SRAM, and set LIST_HEAD to the next number it recorded. Once read, this chunk is empty too, so its own number goes in as well: one refill adds 170.
    • Spill: when the SRAM has more than 448 numbers, take one number from the SRAM as the new list chunk, write the old LIST_HEAD and 169 numbers into it, then point LIST_HEAD at it. The SRAM thus loses 170.

    The two thresholds are far apart: after a refill there are at most 233 numbers, and after a spill at least 279, so the stack never spills right after a refill and shuttles back and forth. One compression uses at most 7 chunks, and a refill is triggered only when the count drops below 64, which leaves plenty of margin to wait for DRAM to respond. Each move is just one 512B DRAM access, and it happens on average once every 170 pops or returns. At boot, the RO objects already occupy the chunks at the start of the pool; the kernel issues one initialization command, and the accelerator writes the remaining chunks as a linked list of list chunks. Only when both the SRAM and the list chunks run out does it report POOL_FULL. The example at the end of Section 12 has only 24 chunks, so the whole stack fits in the SRAM; no list chunk appears there, and LIST_HEAD stays 0xFFFFFF.

    CTLB: do not keep looking up the COT

    The COT is in DRAM, and every lookup waits for DRAM. While decoding an object, the next chunk number is needed every time the chunk changes; if each one were a lookup, 5 chunks would cost 5 extra DRAM reads. But the 32 bytes read the first time already contain all the numbers, so it is enough to keep them in a small cache inside the accelerator. That is the CTLB.

    It serves the same purpose as the TLB of the CPU, but is much smaller. The SoC in this document has only one engine and decompresses one object at a time, so the CTLB holds only 1 entry: the 32-byte COT entry of the object currently being decompressed. When the next object starts, the old entry is overwritten.

    Holding more entries would not be faster. An RW object is freed as soon as it is decompressed; an RO object stays forever, but it is read again only after the page is evicted from the frame cache and then used again, which is a long time later, and by then the CTLB has long since moved on to other objects. The table below shows the number of COT reads when 3 different objects, each with 5 chunks, are decompressed one after another:

    CTLB entriesCOT readsReason
    0 (no CTLB)15One read per chunk change: 3 × 5
    13One read per object, at its start
    10003The 3 objects are all different; no matter how many entries are kept, none hits

    The TLB of the CPU is different: programs access the same set of pages over and over, so more entries raise the hit rate. The CTLB needs more entries only when the hardware handles several objects at once, for example 4 engines need 1 entry each; loading the entry of the next queued job early also costs 1 more.

    Even with only 1 entry, the old data stays in the CTLB after the job ends. So when an RW object is freed, the kernel has to issue an INVALIDATE command to clear it: when the same page is compressed again later, a new chunk list is written under the same handle, and if the CTLB still held the old one, it would read the wrong chunks. RO objects are never freed and do not need this step.

    Putting it all together

    Evicting an RW page (compression):

    1. The kernel computes the handle from the VA and hands the PA of the frame and the handle to the accelerator.
    2. The encoder produces output; every time 512B fill up, the LZ4 MMU pops a chunk from the stack and writes into it.
    3. When done, the length and the chunk numbers are written into the COT entry for the handle.
    4. The kernel keeps the PTE invalid and returns the frame to the frame cache.

    These 4 steps are the summary. Below, step by step, is what the kernel and the accelerator each do, and what the PTE, the descriptor, the stack and the COT entry contain at every step. The page is still the RW page above: VA 0x7F12_3456_7000, handle 0x14567, currently in frame 0x9A2B_4000. Its contents borrow the text sample from Section 5, which compresses to exactly 2296 bytes and 670 sequences, consistent with the earlier examples; which sequence each chunk boundary falls in and what the checksum is are computed by the LZ4 code running on this page. The chunk numbers of the other pages in the stack are illustrative values.

      Evicting an RO page: just invalidate the PTE and return the frame to the frame cache. The compressed object has been in the pool since boot, so the accelerator is not involved at all.

      Decompression (bringing the page back):

      1. The CPU touches an invalid PTE and a page fault occurs. The kernel computes the handle from the VA and prepares a frame.
      2. The LZ4 MMU reads the COT once, gets the length and the chunk list, and keeps them in the CTLB.
      3. The decoder requests bytes sequentially, and the LZ4 MMU turns each request into a PA inside a chunk. The restored data is written to the frame.
      4. The kernel sets the PTE valid, pointing at this frame. If the object is RW, it then issues INVALIDATE to free it and return the chunks to the stack; an RO object is left as it is.

      Some time later the same page is used again. In the meantime, other pages were decompressed and returned many chunks, so the SRAM of the stack has grown from 232 to 446 numbers, and this time a spill occurs; the last object decompressed was RO page 0x1A3F1, whose entry is still in the CTLB.

        An untouched RW page (.bss, heap, stack) has no object, and its COT valid flag is 0. When it is first used, the kernel simply allocates a frame and zero-fills it; the accelerator is not needed.

        Side by side with the CPU MMU

        Both MMUs translate addresses, but they solve different problems. The CPU MMU faces “random access at arbitrary locations”, so it uses fixed-size pages plus multi-level tables. The LZ4 MMU faces “a data stream that reads a whole page from start to end”, but the data size varies, so it uses a one-level table that records scattered chunks.

        Contents of a COT entry (32 bytes)

        FieldSizePurpose
        valid, flags1 byteWhether the object exists; RO means read-only, never freed; RAW means stored uncompressed
        chunk_count1 byteHow many chunks are used (1 to 7)
        comp_len2 bytesCompressed size in bytes; the decoder uses it to detect the end of input
        checksum4 bytesComputed during compression and compared at the end of decompression; catches data corruption
        chunk[0..7]24 bytes3 bytes each. 275 MiB ÷ 512B = 563,200 chunks, so 20 bits would do; 3 bytes leave headroom

        The threshold for run-time compression is 7 chunks, so an RW object uses at most 7. The 8th slot is for RAW mode: an RO page that does not compress at build time cannot simply be left in a frame, so it is stored instead as the uncompressed 4096 bytes, exactly 8 chunks, and the decoder just copies them. comp_len matters too: the tail of the chunk usually has unused space, and the decoder must know where the real end is, otherwise it cannot recognize the last sequence.

        The size of the COT is set by the compressible range: one fixed entry per page, so a 580 MiB range needs 148,480 entries, about 4.5 MiB. The entry exists whether or not the page is currently compressed, so handles never need to be allocated separately.

        Why not share the CPU MMU?

        • Variable size: a CPU page table cannot express “2296 bytes stored in 5 scattered 512B chunks”. Mapping them to a contiguous VA would work too, but every time the page table would have to change and a shootdown would follow; the overhead is too high.
        • No faulting halfway: a hardware pipeline stalled halfway waiting for the OS to respond would be complicated, so the kernel pins the frame and prepares the object first, and the LZ4 MMU only reports the result.
        • Security isolation: the CPU does not need to see the pool directly, which removes one path by which a bad pointer could corrupt compressed data.

        In real products the frame port usually also goes through an IOMMU/SMMU, so that the addresses the device sees are protected too. This document leaves that layer out to keep the contrast between the two MMUs clear.

        11. Page states

        RO pages and RW pages have different states: an RO page's compressed object is in the pool from boot, and only its frame comes and goes; an RW page works like ordinary memory compression, where the page is either in a frame or in the pool, untouched pages excepted.

        How many copies of a page are in DRAM

        Compressed data lives in chunks of the pool; the COT is only an index that records the length and the chunk numbers. A page can have one uncompressed copy in DRAM (in a frame), one compressed copy (in the pool), both, or neither:

        PageUncompressed onlyCompressed onlyBothNeither
        RWIn useAfter evictionOnly briefly, during compression or decompressionUntouched
        RONeverWhen not in the frame cacheAlways, while in the frame cacheNever
        PinnedAlwaysNeverNeverNever

        When an RW page is compressed, the frame stays while the accelerator writes the chunks; the kernel frees the frame only after COMPRESS completes. On failure the chunks already popped are returned and the page stays in the frame only. When an RW page is decompressed, the chunks stay while the decoder writes the frame; the kernel issues INVALIDATE to free the object only after the PTE is set valid. RO deliberately keeps the compressed copy, so that eviction only has to drop the frame.

        How many “compressible but currently uncompressed” pages can exist at once: exactly as many pages as the frame cache holds, at most 140 × 256 = 35,840. Right after boot it is the 6,656 pages of .data; at RW peak it is 7,680 hot RO pages plus 20,480 hot RW pages, 28,160 in total, and the remaining 7,680 frames are margin. In contrast, only one page is being decompressed or compressed at any time, because the accelerator in this document has a single engine; other requests wait in the submission ring and are processed in order.

        malloc() as an example

        Memory obtained from C's malloc() comes from the heap, and the heap is in the RW part of the compressible range, so the memory it allocates can be compressed. The example below uses p = malloc(10000) and assumes it returns p = 0x7F12_2B1C_0F80. These 10000 bytes span 4 pages, handles 0xB1C0 to 0xB1C3.

        Just allocated: when malloc() returns. malloc() is a C library function. What it does:

        1. It looks for a large enough free block in the heap it manages. This heap is a VA range it obtained from the kernel earlier.
        2. When there is no room, it asks the kernel for more VA, for example through brk or mmap. The kernel only records that “this VA range is now usable”: the PTEs stay invalid, no frame is allocated, the COT and the accelerator are untouched, and DRAM does not change at all.
        3. It writes a small header in front of the block, for example 16 bytes recording the size, then returns p.
        Page (handle)State when malloc() returns
        0xB1C0The header is in this page (0x7F12_2B1C_0F70). malloc() touched this page when it wrote the header, so the page has already gone through the “first access” flow below
        0xB1C1–0xB1C3Untouched: PTE invalid, no frame, COT valid is 0

        So malloc(10000) does not immediately consume 10000 bytes of DRAM; it only reserves VA.

        First access: for example a write to p + 5000. p + 5000 = 0x7F12_2B1C_2308, in page 0xB1C2:

        1. The CPU MMU's TLB misses, the walker walks the page table, finds the PTE invalid, and raises a page fault.
        2. The kernel confirms that this VA is inside the allocated heap range, so it is not a program error; if it were outside, the program would be killed.
        3. The kernel computes handle 0xB1C2 and sees that COT valid is 0: this page has never been used, so the accelerator is not needed.
        4. It takes an empty frame from the frame cache. If the frame cache is full, another page must be evicted first: an RO page just drops its frame, an RW page must be compressed first. Only this step may use the accelerator.
        5. It zero-fills the whole frame. This step cannot be skipped, or the program would read data left behind by the previous user.
        6. It sets the PTE valid and writable, pointing at this frame, then returns from the fault.
        7. The CPU re-executes the write instruction, and this time it succeeds.

        A first read follows almost the same flow, and every value read is 0. Linux has an optimization: on a first read-only access it maps a system-wide shared, read-only frame full of zeros, and only allocates a real frame on the first write, so a page that is only read never occupies memory. Later reads and writes to the same page do not fault; every other page repeats this flow when it is first touched.

        Later: when this page turns cold and the frame cache runs short again, it is compressed into an RW object; when it is used again it is decompressed back into a frame and the object is freed, which is the RW path in the state diagram above. On free(p), the allocator usually just marks the block reusable; the page is not returned to the kernel, the now-useless data still occupies a frame, and once cold it may even be compressed into the pool. If the allocator tells the kernel “this range is no longer needed” through a mechanism such as madvise, the kernel can drop the frame or free the object directly, returning the page to the “untouched” state.

        When ordinary malloc() cannot be used: DMA buffers and memory for HRT. Device accesses do not trigger page faults, and HRT cannot afford to wait for decompression, so this memory must be allocated from the pinned region; the 22 MiB of run-time data in the pinned region in Section 9 is reserved for this. An alternative is to lock the page temporarily while it is in use, so that it is not evicted.

To see how several pages change from boot onward, see From boot to run time at the end of this section.

          Locks between flows

          Several threads may touch the same page at the same time. The first thread to fault does the decompression; the faults of the other threads see that the page is being processed and wait on the lock. The kernel must also handle the case where someone needs the page while it is still being compressed: wait for the compression to finish and then go straight to decompression, or cancel the swap-out.

            • Chunk order has no meaning: compressing H1 at step 16 gets 0x10, 0x0F, 0x0E, 0x11, because D has just returned its chunks to the stack. Only the list in the COT can find them again.
            • Failures leave no trace: when a page is incompressible (H2) or the pool runs short (H3), the chunks already popped are returned, the COT is not written, and the page stays in its original frame.

            13. Latency and capacity

            All default values in these two calculators are assumptions, meant for understanding the trade-offs, not measured results. The defaults of the second calculator are the assumed measurements from Section 9; replace them with the numbers you measure yourself.

            How long one compressed page fault takes

            Decompression itself is often not the largest cost: trapping into the kernel, allocating a frame and updating the page table all take time. So hot pages should not be compressed; when a page is swapped in and out repeatedly, no accelerator is fast enough to help.

            How big DRAM must be: starting from measurements

            The arithmetic is the same as in Section 9: COT = number of compressible pages × 32 B; the frame cache must at least hold the hot RO and the hot RW; the pool must at least hold all RO objects plus the compressed size of the cold RW. What is left is margin, to be split between the frame cache and the pool. The compression ratio must include rounding up to 512B chunks.

            14. HRT and QoS

            HRT data is protected by three mechanisms, and none of them can be left out:

            • Placement: HRT code and data are in the pinned region of the image, and the display buffer is in the carve-out. Neither is in the compressible range, so reclaim never even sees them.
            • Path: the display goes straight through the interconnect to DRAM; it does not pass through the accelerator and does not look up the COT.
            • Bandwidth: the accelerator generates a lot of DRAM traffic, so the arbiter must give HRT higher priority and limit the accelerator's burst size and rate.

            How this differs from your earlier premise. Your earlier premise was that “all clients go through the same compression layer”. The hardware in this document is a page-level accelerator that takes part only when pages are swapped in or out; neither HRT nor ordinary accesses go through it.

            Compared with the earlier comparison figure, it is closest to Option C, since in both the OS picks the cold pages; the difference is that here even a read must fault and decompress first, whereas the inline hardware of Option C can read directly. The advantages are that the main DRAM path is untouched and physical memory cannot silently run out: when the pool is full, the accelerator just reports POOL_FULL, the kernel drops the frame of an RO page instead, and no data is lost. Which data can be compressed is decided at build time by the two regions of the image.

            Verification and sources

            What was verified

            • Encoder: compared against lz4 v1.10.0 on 456 data sets. For 432 of them the tool emitted a compressed block, and the output of the code running on this page is byte-for-byte identical; for the other 24 the tool stored the data uncompressed, so the contents were not compared.
            • Decoder: the code running on this page decodes the 432 blocks from the tool; the tool also decodes the 456 blocks produced by the code running on this page.
            • Size formulas: the formulas in Section 2 for the restored, occupied and saved sizes were evaluated on all 456 blocks from the code running on this page and on the 432 compressed blocks from the tool; the totals equal the sizes of the original data and of the blocks every time.
            • Match measurements: the 94% in Section 1 and the table in Section 3 were computed by shapes.js and overlap.js in lz4-verify, on synthetic data and on files on this Mac.
            • Error handling: an offset of 0, an offset out of range, literals running past the input, and output exceeding the limit are all rejected, and tests cover each.
            • The table in Section 6: produced by actually running this code; the compressed sizes agree with the tool. The 4114 bytes for random data is the block size from the code running on this page; the tool instead stores an uncompressed block of 4096 bytes at the file level.
            • Address examples: the VA split and PA in Section 10, and the region addresses and sizes in Section 9, were all computed by code.
            • The three step-by-step demos in Sections 9 and 10: the compressed size, which sequence the chunk boundary falls in, the contents of the first token and the checksum are computed by the LZ4 code on this page; the addresses were checked with plan512.py; the state at each step is accumulated by the code running on this page. The chunk numbers of the other pages in the stack, the ring slot numbers and the tags are illustrative values.
            • The 8-page example in Section 12: the state at each step is produced by simulation in the code running on this page, and the compressed sizes are computed by the LZ4 code on this page; each eviction was checked to pick the least recently used page.

            What was not verified

            • The hardware and flows of Parts B and C are a teaching example designed from first principles; there is no RTL and no simulation. An implementation may run into problems not considered here.
            • The latency and speed numbers are all assumptions. The hot-data sizes in Section 9 (RO 30 MiB, RW 80 MiB) and the compression ratios (RO 55%, RW 45%) are also assumed measurements; measure them on your own system.
            • The sample data is synthetic and does not represent your workload.
            • Why the end-of-block rules exist, and implementation techniques such as the generation tag, come from my prior knowledge; the specification itself does not explain them.
