每個 page 一列：PTE、兩個 core 的 TLB、內容在哪裡、哪些 cache 有一份

PTE 只有一份，在 DRAM 裡，只有 kernel SW 讀寫。TLB 每個 core 一份，是 kernel SW 照 PTE 抄進去的。CPU MMU 只看自己那個 core 的 TLB。兩邊說的不一樣時，那一格標成 STALE。最後一欄是這個 page 所在的 frame 目前在哪些 cache 裡有一份，哪一份比 DRAM 新。這一步有變動的格子會標色。

這一頁照專案的平台前提畫：CPU MMU 沒有 hardware page table walk，TLB miss 之後一律進 exception，由 kernel SW 讀 page table 並填 TLB。每個 core 一個 TLB 是目前的假設，還沒有對過 CPU 手冊。

範例的部分：TLB 畫 3 格、滿了輪流蓋掉、讓出 frame 的是最早拿到 frame 的 page、2 個 core、每個 core 2 個 hardware thread、6 個 page、4 個 frame。平台的 TLB 有幾格、怎麼取代，目前不知道。壓縮後資料畫的寬度只表示變小，不是量出來的大小。

Cache 的畫法是範例：每個 frame 在每個 cache 裡只有「沒有、有一份、比 DRAM 新」三種狀態，cache 永遠放得下。兩個 core 之間怎麼交接比較新的那一份，畫的是一種常見的做法，不是這個平台查到的行為。L1 與 L2 的大小目前不知道。Kernel SW 自己讀 page table 也會經過 cache，這一頁沒有畫。

Kernel SW 在把 frame 交給 LZ4 HW 之前做 cache clean，在 LZ4 HW 寫完 frame 之後做 cache invalidate，原因是 LZ4 HW 直接讀寫 DRAM，看不到 CPU 的 cache。用哪一個指令、怎麼讓其他 core 的 L1 也照做，這個平台目前不知道，圖上標成 not known。

一個 core 上的 kernel SW 用什麼機制清掉另一個 core 的 TLB，這個平台目前不知道。場景 7 只畫出結果。同一個 core 的兩個 hardware thread 同時改 TLB 時 CPU 有什麼限制，也不知道。場景 5 只畫兩個 thread 一前一後。

場景 8 的錯誤，在 host simulation 裡有一個故意改壞的版本與它對應：只清自己那個 core 的 TLB。測試會抓到它，訊息是 StaleTlb。

場景 9 與 10 的順序照 host simulation 的 kernel：改表的時候拿著 mm_lock，等 LZ4 HW 的時候不拿，page 的狀態寫在 kernel 自己的表裡，PTE 最後才設成有效。只填 TLB 的 TLB miss handler 要不要拿 mm_lock，目前沒有設計，這一頁畫成不拿。

簡化的部分：這一頁由發生 page fault 的那份 kernel SW instance 自己把別的 page 趕出去，而且等到 frame 用完才做。實際的設計由另一個 reclaimer 在空 frame 低於門檻時先做，fault 的那一邊只在沒有空 frame 時等它。

壓縮層在這一頁只算一步。壓縮後的資料放在哪裡、LZ4 HW 怎麼讀寫，見 address 動畫 與 3D 課程。
