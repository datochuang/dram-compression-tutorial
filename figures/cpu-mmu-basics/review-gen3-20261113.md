## 冷讀者自己講的結論

gen2 那一輪讀完三張，原文：

> 程式用的 address 不是記憶體真正的 address。每一次存取，CPU 都要把「哪一個 page」換成「DRAM 裡的哪一個 frame」，page 裡面的 offset 不變。完整的對照表（page table）放在 DRAM 裡，由 kernel SW 維護。CPU 的硬體不會自己去讀它，只看 CPU 裡一份很小的副本（TLB），這份副本也是 kernel SW 填的。每個 core 各有一份副本，副本不會自己更新。所以 kernel SW 要收回一個 frame 時，要先把 PTE 改成 invalid，再把每一個 core 的 TLB 裡那一筆清掉，最後才能動那個 frame。漏掉一個 core，那個 core 會繼續直接讀寫舊的 frame，kernel 不會收到任何通知。

gen3 那一輪對重畫的 C，遮住 Key point 時寫的一句話，原文：

> kernel 要收回一個 frame 時，先把 page table 裡那一筆 PTE 改成 invalid，再把每一個 core 的 TLB 裡那一筆清掉，自己的 core 和其他 core 都要清，然後才能清空並重用那個 frame；少清一個 core，那個 core 上的 user SW 會繼續 TLB hit、直接讀寫舊的 frame，而且不會有 exception，kernel 攔不到。

## 記錄不改的小瑕疵

A：

- 兩條帶子各畫了六格，提示詞寫的是五格。格數不帶意思。
- `0x00416C80 = page 0x416 + offset 0xC80` 的加號會被讀成加法。實際是把兩段接起來。`README.md` 的表用「商」與「餘數」說明。
- page 用編號，frame 用起始 address。這是 `README.md` 例子本來的寫法。
- `Translation` 沒有說是誰做的。B 回答這件事。

B：

- 畫面沒有 TLB miss 的時候發生什麼事。這是白板圖 2 的內容，`README.md` 的閱讀順序把它排在 B 的後面。
- 藍色的 no arrow here 說明離紫色的 kernel 箭頭很近。
- 底下的 Key point 寫 Hardware never reads，畫面寫 CPU MMU never reads。

C：

- page table 多了一列空白。冷讀者讀成「還有其他列」。
- 橘色往 frame 的箭頭和正常 access 同一個顏色，沒有警示。要讀右上角的卡片才知道它是危險的來源。
- frame 畫成空白方格。畫面的時間點是第 1 步之後、第 2 步之前，這時 frame 裡還有 page 0x416 的資料。
- `drawn after step 1, before step 2` 在 page table 的正下方，像是 page table 的註腳。它說的是整張圖。
- 標題的 Clear Every TLB 可能被讀成清空整個 TLB。內文與 Key point 說的是清掉那一筆 entry。
- 兩支箭頭都標 2，第 3 步只有文字、沒有箭頭。
- Core 1 上的 kernel 怎麼清到 Core 0 的 TLB，圖沒有說。這是平台還不知道的事，見專案 `CLAUDE.md`。圖上不畫機制是刻意的。

## 只看這三張時的洞

冷讀者指出：`exception` 與 `TLB hit` 在 C 才第一次出現，C 右上角的「no exception happens, so the kernel cannot stop it」需要讀者先知道 TLB miss 會產生 exception。A 與 B 沒有教這件事。

這不是 C 能補的。`README.md` 的閱讀順序是 A、B、`figures/system-overview/` 的白板圖 2、1、3，然後才是 C。白板圖 2 教 TLB miss 與 exception，白板圖 1 教每個 core 一張 TLB。這三張不要脫離那個順序單獨使用。
