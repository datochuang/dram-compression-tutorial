第 3 張在 gen2 沒過的主因是提示詞寫錯了一句：Key point 的「nobody holds it while the LZ4 HW works」。同一個時刻左邊的 instance 正握著 `mm_lock`，而 LZ4 HW 正在替右邊的 instance 工作。正確的說法是「在等自己 job 的 instance 不握 lock」。

## 冷讀者自己講的結論

gen2 那一輪讀的是完整四張，原文：

> 這顆 SoC 的每個 core 有自己的 MMU／TLB 與 L1，所有 core 共用 L2 與 DRAM。CPU 硬體不會自己查 page table，所以每一次 TLB miss 都在當下那個 thread 上進 kernel，由 kernel 查表、填 TLB。如果那個 page 是壓縮的，kernel 就在這條路上請 LZ4 HW 解壓縮。
>
> 好幾個 thread 會同時在 kernel 裡，共用的表用一把 `mm_lock` 保護，一次只進一個，等 LZ4 HW 的那段時間不拿這把鎖。LZ4 HW 只有一個，裡面有 N 個 engine，所有 core 透過同一個 job ring 送 job，`ring_lock` 只管排進去那一下。結果照做完的順序回來，用 tag 對回去。資料由 LZ4 HW 直接讀寫 DRAM，不經過 L1、L2，所以 kernel 要自己在前後處理 cache。

gen4 那一輪只讀第 4 張，原文：

> 整顆 SoC 只有一個 LZ4 HW，所有 core 的 kernel SW 把工作丟進同一個 ring。丟的時候要搶一把鎖，那把鎖只管排進去這一下。HW 裡 N 個 engine 同時做，誰先做完誰先回報，所以回報順序和排隊順序不同，kernel SW 靠 tag 認領。page 資料由 HW 直接對 DRAM 讀寫，不走 CPU 的 cache，所以 kernel SW 要在 COMPRESS 前做 cache_clean、DECOMPRESS 後做 cache_invalidate。

## 整組沒有講的事

兩次冷讀都指出，這些不在這四張的範圍裡：

- 誰發起 COMPRESS。
- 一次 decompression fault 的全程。第 2 張停在 TLB refill，第 4 張停在 interrupt。
- `mm_lock` 與 `ring_lock` 的先後關係。
- 第 2 張讀 page table 沒有畫 lock，第 3 張的 page table 在 `mm_lock` 裡。讀者會問每一次 TLB miss 要不要拿這把 lock。這一點控制程序文件還沒有照平台前提 P1 寫，是未定的設計問題，不是圖的問題。
