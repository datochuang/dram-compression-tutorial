第四版在 `gen11/`，紀錄在 `review-gen11-20261115.md`。負責人指出第四版最大的字 ONE SHARED SET 會誤導：ONE 擺在 one module 旁邊，讀起來像壓縮層只有一份。負責人的原則：一個頁面最大的字不能有誤導空間。

| 項目 | 結果 |

| 決定 | 不採用。負責人選擇改版面 |

## 第六版，gen13，採用

提示詞在 `prompts.md`。版面改成三排：
- 上排是橫跨全寬的 processor。每個 core 裡有 CPU MMU and TLB、藍色虛線框的 TLB miss handler、綠色虛線框的 compression kernel SW，兩者之間一個 a call 箭頭。卡片外框的顏色表示由哪一邊設計。
- 中排是兩個 domain frame，只放各自的表與硬體幫手。藍框是 page table。綠框是 COT、chunk pool、LZ4 HW 寫 several engines、future HW assists 貼 PROPOSAL。
- 大字只講硬體幫手的位置：HW HELP: INSIDE EACH CORE 對 HW HELP: BESIDE THE LZ4 HW。
- 表格拿掉。

| 回合 | 檔案 | 做了什麼 | 結果 |
|---|---|---|---|
| 1 | `gen13/03-apart-even-in-software.png` | 第六版提示詞 | 46 條文字全對，四個箭頭不交叉、不穿過介面框。往下的兩個箭頭畫成橘色，應該是紫色 |
| 2 | `.r2.png` | edit：兩個箭頭與標籤改成紫色 | 只有這兩個箭頭改變 |

冷讀讀的是第 1 回合，兩回合只差兩個箭頭的顏色。報告 `blind-review/cold-read-gen13-20261115.md`。

| 項目 | 結果 |
|---|---|
| 困惑指數 | 2 |
| 最大的字 | 主詞讀成兩邊的硬體幫手，講位置。沒有讀成壓縮層 kernel SW 只有一份 |
| 執行方式的讀法 | 在 fault 的 core 上由 TLB miss handler 呼叫，好幾個 core 可以同時各跑一份，碰到 COT 與 chunk pool 時排隊拿 lock |
| 畫面與結論 | 部分一致，落差只在用詞 |
| 決定 | 採用 `.r2` |

冷讀者自己的結論：這張圖承認壓縮的 kernel SW 是 TLB miss handler 在 fault 的那個 core 上呼叫的一段程式，好幾個 core 可以同時各跑一份。它主張分開設計的理由不是跑在不同地方，而是依賴的硬體在不同地方。

## 記錄不改的小瑕疵

| 項目 | 說明 |
|---|---|
| 往下的兩個箭頭 | 一條從 Core 0 下方出發，一條從 Core 1 下方出發，可能讀成 Core 0 管 CPU MMU、Core 1 管壓縮 |
| 表在不同地方 | 副標題與 Key point 說兩邊的表在不同地方，畫面上兩邊都標 in DRAM。比較準的說法是由不同的一方擁有 |
| 用詞 | Key point 寫 fault path，畫面寫 TLB miss handler |
| THE LZ4 HW | 單數，要看到 several engines 才知道有多個 engine |
| HW HELP | 指 LZ4 HW 本身還是 future HW assists，兩種讀法都說得通 |
| 圖例 | 虛線與填色的意思沒有說明，COT 沒有全名 |
| 雜點 | interface 框下方有一個小點 |

## 冷讀者沒被擋住的反駁

| 反駁 | 說明 |

| PTE 格式 | handler 靠它判斷要不要進壓縮層，壓縮層要改寫它，本身就是耦合 |
