A. LZ4 演算法

1. 核心想法

LZ4 只做一件事：遇到前面出現過的資料，就不再存一次，改記「往回幾格、複製幾個」。沒出現過的資料就原樣存下來，這種原樣存放的 byte 叫 literal；往回複製的部分叫 match。

資料會被切成一段一段，壓縮後只存兩種東西：

  • Literal bytes：找不到重複、只能照存的 byte。
  • Descriptor：告訴解碼器這一段怎麼還原。每段都有一個，而且都回答同樣三個問題：照存幾個 byte、往回幾格、複製幾個。

解壓縮時，解碼器一段一段照著 descriptor 做：

  1. Descriptor 1：照存 14 個 byte，得到 say:hello-bob-。接著從現在的位置 14 往回 10 格，也就是位置 4，複製 5 個，得到 hello。
  2. Descriptor 2：照存 7 個 byte，得到 ,again!。這一段沒有東西要複製，還原到此結束。

第 2 段不是格式不同，只是 back 和 copy 沒有內容。資料的最後一段一定是這樣，原因在下一節的結尾限制。

同一種 descriptor，也能複製很多份

上面的 hello 只複製一份，而且來源完整存在。但 copy 可以比 back 大，這時同一小段資料會被複製很多份。最高的壓縮率通常就出現在這種情況。

複製時是一個 byte 接一個 byte：位置 5 拿位置 3 的 a，位置 6 拿位置 4 的 b，位置 7 再往回 2 格，拿到的是位置 5 剛複製好的 a。所以 ab 會一直重複下去，直到複製滿 18 個。

Descriptor 的形式和前一個例子完全相同，只有數字不同。這個 29 bytes 的字串可以壓成 15 bytes。更極端的情況是 4096 個 0x00，只要 26 bytes，第 3 節會專門介紹。

最常見的情況：來源在更早的段落

前兩個例子的來源都在同一段的 literal 裡，只是因為這樣容易畫。實際把資料切成 4KB 壓縮時，94% 以上的 match 來源在更早的段落，也常有完全沒有 literal 的段落。下面這個例子同時呈現這兩件事：

  1. Descriptor 1：照存 11 個 byte，得到 a:owl,blue,。接著從位置 11 往回 9 格到位置 2，複製 4 個，得到 owl,。
  2. Descriptor 2：照存 3 個 byte，得到 red。接著從位置 18 往回 13 格到位置 5，複製 6 個，得到 ,blue,。來源在第 1 段。
  3. Descriptor 3：照存 0 個 byte。直接從位置 24 往回 18 格到位置 6，複製 5 個，得到 blue,。
  4. Descriptor 4：照存 7 個 byte，得到 end-now。沒有東西要複製，還原結束。

這裡可以看出兩件事。第一，back 和 store 沒有關係：第 3 段照存 0 個，卻可以往回 18 格，因為來源可以是任何已經還原的資料，不管它當初是照存的，還是複製出來的。第二，descriptor 的形式始終不變，三個例子只有數字不同。

LZ4 的設計重點是速度：它不做 Huffman 這類 entropy 編碼，所有長度都對齊 byte，解壓縮時不用逐 bit 解碼，只需要反覆複製資料。代價是壓縮率比 zstd、Deflate 低。

2. Byte 格式

先看上一節的 hello 例子，它的兩個 descriptor 可以念成兩段話：「第 1 段：照存 14 個 byte，往回 10 格、複製 5 個。第 2 段：照存 7 個 byte。」這一節只做一件事：把這兩段話寫成 bytes。

本文的數字寫法

  • 沒有前綴的數字都是十進位：長度、offset、位置都這樣寫，例如 12、280。
  • 前面有 0x 的是 16 進位：A 到 F 代表 10 到 15，例如 0xE = 14、0x0A = 10。
  • 格子裡的單一字元就是 literal：例如 s。實際存的是它的 ASCII 值，s 就是 0x73。空白顯示成 SP，無法顯示的 byte 才用 0x.. 表示。

難處在於，解碼器拿到的只是一串數字，沒有人告訴它哪裡是文字、哪裡是長度，所以每個值放在哪裡必須事先約定好。先處理第 1 段：descriptor 的三個值加上 literal 本身，共有 4 件事要存：

Token 不是一個數字，而是兩個各佔 4 bits 的欄位。下圖把 0xE1 拆開，同一組 bits 分別用三種進位寫出來：

前面兩張圖裡有三個約定，它們就是整個格式的核心：

  • 兩個長度放最前面。解碼器要先知道有幾個 literal，才知道文字到哪裡結束、offset 從哪裡開始。14 和 5 都是小數字，各用 4 bits 就放得下，所以合併成 1 個 byte，這個 byte 叫 Token。14 就是 0xE，放在高 4 bits。
  • Match 長度存「長度減 4」。一個 match 至少要花 2 bytes 的 offset，通常還要多一個 Token，比 4 更短的 match 幾乎省不到空間，所以 LZ4 規定最短就是 4。既然不會小於 4，存 0 就代表 4，5 則存成 1，也就是 0x1，放在低 4 bits。兩個欄位合起來，Token 就是 0xE1。
  • Offset 固定 2 bytes，低位在前（little-endian）。讀回來的算法是「第 1 個 byte + 第 2 個 byte × 256」。0x0A 就是 10，所以 0x0A 0x00 = 10 + 0 × 256 = 10。再看一個大一點的：offset 300 存成 0x2C 0x01，其中 0x2C 是 44，0x01 是 1，所以是 44 + 1 × 256 = 300。2 bytes 最大可以表示 65535，所以最多往回約 64KB，更遠的重複資料就不能參考。

所以 descriptor 在真實格式裡不是獨立的一塊，而是拆開放在 literal 的前後：照存幾個和複製幾個放進 Token，往回幾格放進 offset。Token、literal、offset 這一組就叫一個 sequence，一個 LZ4 block 就是一連串的 sequence。

Descriptor 只是本文為了說明取的稱呼，LZ4 規格沒有這個詞，它也和第 8 節加速器工作用的描述子無關。

14、10、5 是三個互相獨立的數字

  • Literal 長度 14：這個 sequence 新存了幾個 byte。
  • Offset 10：從現在要寫的位置往回幾格找來源。現在要寫位置 14，所以來源在 14 - 10 = 位置 4。
  • Match 長度 5：從來源複製幾個 byte。

Offset 也可以比 literal 長度大，因為來源可以在更早的 sequence 裡。後面 63 bytes 例子的第 4 個 sequence，literal 長度是 0，offset 卻是 23。

讀回來：解碼器怎麼看這些 bytes

第 2 段「照存 7 個 byte」也要一個 sequence，整個 block 就完成了。這次換成解碼器的角度，從左讀到右：

  1. 第一個 byte 一定是 Token。0xE1 拆成 0xE 和 0x1：接下來有 14 個 literal，之後要複製 1 + 4 = 5 個。
  2. 照抄接下來的 14 個 byte，輸出 say:hello-bob-。
  3. 再讀 2 bytes 0x0A 0x00，得到 offset 10。現在要寫位置 14，往回 10 格就是位置 4，從那裡複製 5 個，輸出 hello。第 1 個 sequence 到此結束。
  4. 下一個 byte 又是 Token。0x70 的高 4 bits 是 0x7，代表 7 個 literal。低 4 bits 的 0x0 這次不會用到，原因在下一步。
  5. 照抄 7 個 byte，輸出 ,again!。這時輸入剛好讀完，解碼器就知道這是最後一個 sequence。最後一個 sequence 只有 literal，沒有 offset，也沒有 match，所以 Token 的低 4 bits 沒有作用。

第二個例子：複製很多份的 bytes

第 1 節的 go:abab... 也用同樣的規則寫成 bytes。第 1 段的 descriptor 是照存 5、往回 2、複製 18：

加上第 2 段的 sequence，整個 block 是 15 bytes。解碼器一樣從左讀到右：

  1. 讀 Token 0x5E：高 4 bits 是 0x5，接下來有 5 個 literal；低 4 bits 是 0xE，也就是 14，之後要複製 14 + 4 = 18 個。
  2. 照抄 5 個 byte，輸出 go:ab。
  3. 讀 2 bytes 0x02 0x00，得到 offset 2。現在要寫位置 5，往回 2 格是位置 3。接著逐 byte 複製 18 個，輸出的是 ab 重複 9 次。
  4. 讀下一個 Token 0x60：接下來有 6 個 literal。
  5. 照抄 6 個 byte，輸出 ,done!。輸入讀完，解壓縮結束。

Bytes 裡沒有任何欄位標示「這是複製很多份」。它和 hello 例子的格式完全相同，差別只在數值：match 長度 18 比 offset 2 大。解碼器不必先判斷是哪一種，只要一律由前往後逐 byte 複製，兩種情況都會得到正確結果。第 3 節會再說明逐 byte 複製為什麼重要。

第三個例子：來源在更早的 sequence

第 1 節的 a:owl,... 有 4 段，所以有 4 個 sequence，共 31 bytes。每個 sequence 都照同樣的規則寫：

  • Sequence 1 的 Token 0xB0：0xB 是 11，所以有 11 個 literal。0x0 是 0，所以複製 0 + 4 = 4 個，這是 match 的最短長度。
  • Sequence 2 的 offset 0x0D 0x00：等於 13，比它的 literal 長度 3 大得多，因為來源在第 1 個 sequence 留下的資料裡。
  • Sequence 3 的 Token 0x01：高 4 bits 是 0x0，代表沒有 literal，所以下一個 byte 就是 offset。低 4 bits 是 0x1，所以複製 1 + 4 = 5 個。
  • Sequence 3 的 offset 0x12 0x00：等於 18。這個 sequence 只佔 3 bytes，卻還原 5 bytes。

解碼器遇到這些情況不需要任何特別處理。Literal 長度是 0 就少複製一段，offset 再遠也只要不超過已還原的資料量，都用同一個流程處理。

所有 sequence 都是這個形狀

長度怎麼延伸

14 和 5 都放得進 4 bits，但一段沒有重複的資料可能有 280 bytes，而 4 bits 最大只有 15，也就是 0xF。LZ4 的做法是把 15 當成「還沒完」的記號：欄位填 15 時，解碼器要繼續讀下一個 byte 並加上去；讀到 255 就再讀一個，讀到其他值（包括 0）就停止。

一個 sequence 代表多少資料

  • Literal 長度：Token 高 4 bits。如果等於 15，再加上 Token 後面的延伸 bytes。

  • 它不是所有資料的主要來源：文字和單字表省下的空間幾乎都來自普通 match，例如第 1 節的 hello。

這些只是合成資料和這台 Mac 上的檔案，不是 SoC 實際的記憶體內容。實際比例要用你的 workload 量。

解碼器必做的安全檢查

壓縮資料可能損壞，解碼器絕對不能因此讀寫到範圍外。這些錯誤頁面上的解碼器都會拒絕，硬體也應該全部回報成錯誤狀態：

  • Offset 非法：等於 0，或比目前已輸出的量還大（會指到輸出起點之前）。
  • 輸入超界：Literal、offset 或長度延伸超出 block 尾端。
  • 輸出超界：超過目標大小。對 4KB page 而言，長度必須剛好是 4096。

4. 壓縮

壓縮的工作是找出 match。理論上每個位置都要跟前面所有位置比對，那太慢了。LZ4 用一張 hash table 記住「這 4 個 byte 上次出現在哪裡」，每個位置只查一次，所以很快，但可能錯過更好的 match。

完整步驟

下圖是編碼器的主迴圈。每個方塊都對應下面清單的一步；按清單裡的按鈕，可以跳到逐步示範中第一次出現這一步的地方。示範用的是頁首的 63 bytes 例子。

  1. 查表：讀 ip 開始的 4 bytes，算出 h，從 table[h] 取出候選位置 match，再把 table[h] 改成 ip。表的空格初始值是 0。
  2. 驗證：比對 match 和 ip 開始的 4 bytes。Hash 會碰撞，空格也會指向位置 0，所以這步不能省。這一步只確認可以開始 match，長度還沒決定。
  3. 沒中：ip 前進 step。連續失敗越多跨越越大：大約每失敗 64 次，step 加 1。所以遇到壓不下去的資料時，編碼器會加速跳過。
  4. 往回延伸（catch up）：比較 ip 和 match 前一個 byte，相同就把兩者都往前移，讓 match 更早開始。不能越過 anchor，也不能越過位置 0。
  5. 寫 token 與 literals：anchor 到 ip - 1 是 literals。Token 的高 4 bits 寫 literal 長度，低 4 bits 先空著，接著照抄 literals。
  6. 寫 offset：ip - match，用 2 bytes、低位在前。
  7. 往後延伸：從第 5 個 byte 開始，一次比一個 byte，直到不同或碰到 end - 5。Match 的長度在這一步才決定。
  8. 補上 match 長度：把長度減 4 寫進 token 的低 4 bits，必要時加延伸 byte。ip 和 anchor 都移到 match 的結尾。
  9. 接續：補記 ip - 2 的位置，並立刻用新的 ip 查表。中了就回到第 5 步，寫一個沒有 literal 的 sequence；沒中就 ip 加 1 回到第 1 步。
  10. 收尾：ip 超過 end - 12 就不再找 match，把 anchor 之後的資料寫成最後一個 literal-only sequence。

63 bytes 的例子裡沒有發生往回延伸。前 3 個 match 都做了第 4 步的檢查，但都停在原地：第 1 個的 match 已經在位置 0，另外 2 個的前一個 byte 不同。第 4 個 match 是第 9 步立即查表時找到的，緊接在上一個 match 後面，沒有 literal，也不必往回延伸，所以直接回到第 5 步。

什麼時候產生一個 sequence

Sequence 是「literals 在前、match 在後」，所以編碼器是在找到 match 時才產生 sequence，不是讀到資料就輸出。沒中的位置什麼都不寫，只是留在 anchor 到 ip 之間，等下一個 match 出現時，一起成為它的 literals。產生 sequence 的時機只有三種：

  • 一般查表中了（第 2 步）：寫出前面累積的 literals 加上這個 match。
  • 接續時立即查表中了（第 9 步）：緊接在上一個 match 之後，沒有 literal。
  • 收尾（第 10 步）：最後一個 sequence 只有 literals，沒有 match。

所以 sequence 數 = match 數 + 1。連續沒中再多次也不會切出新的 sequence，只是 literal 長度變長，超過 15 就用延伸 byte 表示。一個 sequence 也不是一次寫完：第 5 步就開始寫 token，到第 8 步補上 match 長度才完成。63 bytes 例子的 5 個 sequence 如下，數字是下面示範的步驟：

8. 軟硬體介面

這裡的 kernel 指跑在 CPU 上的作業系統核心，包括處理 page fault 的 pager 和加速器的驅動程式。它可以是 RTOS 加上一個 pager，也可以是 Linux 這類系統，本文只要求它能處理 page fault。依第 9 節的假設，kernel 的這些部分都在 pinned 區，自己永遠不會被壓縮。

本文讓 kernel 和加速器透過 DRAM 裡的兩個環形佇列溝通。這樣 kernel 可以一次排很多工作，不必等每一個完成。

本文假設這顆 SoC 沒有可以隨時讀回的儲存裝置：image 只在開機時從 flash 讀一次，之後所有內容都必須留在 DRAM。所以連程式碼也要壓縮，才省得到空間。建置時，linker 把每個 section 放進兩段 VA 之一：

Pager 和 LZ4 driver 一定要在 pinned 區：處理 page fault 的程式如果自己被壓縮了，就再也解不開。HRT 的程式和資料也在這裡，因為它們不能等解壓縮。

.data 其實也可以離線壓縮。它的初始值在建置時就確定了，建置工具一樣可以把它壓好，開機時直接放進 pool。和 RO 唯一的差別是 .data 會被寫入：壓縮副本只在 page 還沒被改過時有效，所以第一次解壓縮後就要釋放，之後照 RW 的方式處理。本文的 .data 只有 26 MiB，而且開機後很快就會被用到，所以以未壓縮形式載入。這個選擇會影響剛開機時用了多少 DRAM，但不影響最吃緊時需要的 DRAM。

Compressible 範圍是從 VA 0x7F12_2000_0000 起的 580 MiB：前 332 MiB 是 RW（.data 26 MiB，加上 heap 和 stack 306 MiB），後 248 MiB 是 RO。Handle 就是 page 在這個範圍裡的編號，所以 COT 有 580 MiB ÷ 4 KB = 148,480 格，約 4.5 MiB，配置 5 MiB（第 10 節）。

熱資料與冷資料：壓縮只對冷的有用

要知道能省多少，先要分清楚熱和冷：

  • 熱的 page：最近常被用到。它必須以未壓縮的形式放在 frame cache，因為 CPU 只能讀寫未壓縮的資料。如果把它壓縮了，每次用到都要 page fault 再解壓縮，一次就要好幾 µs（第 13 節），系統會慢到不能用。
  • 冷的 page：很久沒被用到。它可以壓縮後只留在 pool，佔的空間變小；真的又被用到時，才付一次解壓縮的代價。

Kernel 怎麼知道誰冷誰熱：CPU 每次存取一個 page，CPU MMU 會在它的 PTE 設一個 accessed bit。Kernel 定期掃描並清掉這些 bit，一段時間都沒再被設起來的 page 就是冷的。所以「冷」不是 page 固定的屬性，同一個 page 會隨程式的行為在冷熱之間變來變去。

熱和冷的比例是 workload 的特性，不是可以設定的參數。所以設計的第一步是量測：在最吃緊的情境下，統計一段時間內 accessed bit 被設起來的 page 有多少，那就是熱資料；再把記憶體內容一頁一頁用 LZ4 壓縮，得到壓縮比（第 5 節的實驗台就是這個做法）。本文假設量到的結果如下：

  3. 載入 image：Pinned 部分複製到 pinned 區。RO 的 chunk 映像複製到 pool 開頭；建置時就是照這個位置排的，所以 chunk 編號不必修改。RO 的 COT entry 寫進 COT 對應的位置。.data 複製到 frame cache，並建立 valid 的 PTE。

下面把這 5 步拆開，逐步看建置工具產生了什麼、flash 裡放了什麼、boot loader 和加速器的 INIT 指令又各寫了什麼。範例用一個 RO page：VA 0x7F12_3A3F_1000，handle 0x1A3F1，也就是第 12 節第三個流程裡的那一頁。RO page 的內容是程式碼，本頁沒有程式碼樣本，所以借第 5 節的樣本當內容：前 4 個 RO page 依序用文字、指標、隨機、全 0 四種樣本，0x1A3F1 用前 3271 bytes 的文字、其餘為 0；壓縮大小和 checksum 都是本頁的 LZ4 程式實際算出來的。其他 63,483 頁沒有逐一假設內容，只用總量 136.4 MiB。表格裡藍底的列是這一步改變的地方。

    先分清楚 page 和 frame：RO page、RW page 指的是內容：一個 4 KB 的資料，用 VA 稱呼，種類在建置時就決定。Frame cache 裡的 frame 指的是位置：DRAM 裡一格 4 KB 的空間，用 PA 稱呼，在開機時劃好。Page 會在 frame 和 pool 之間搬來搬去，frame 則固定不動，只是裡面放的 page 會換。例如第 12 節的例子裡，RW page H1 先後待過 frame F0、pool 裡的 4 個 chunk、frame F3；frame F0 則先後放過 D、H1、R1、R4。下面的圖用顏色表示內容（綠色 RO、藍色 RW），用所在的區塊表示位置：藍色在 frame cache 裡是未壓縮的 RW page，在 pool 裡是壓縮後的 RW page。

    「空」也要分清楚。空的 frame 是一格目前沒有 page 放在裡面的 DRAM 位置，它佔著 DRAM，裡面是上一個使用者留下的舊資料。還沒用過的 page 是一段還沒放在任何地方的內容，邏輯上全是 0，但不佔任何 DRAM。兩者第一次相遇時，kernel 拿一個空的 frame、清成 0，再把 page 對應過去；解壓縮則不必先清，因為會把 4096 bytes 寫滿。另外，內容全是 0 的 page（例如第 12 節的 R3）是一個真的 page，仍然佔空間：在 frame 裡佔 4 KB，壓縮後 26 bytes，但還是用掉一個 512B 的 chunk。

    RO 物件開機後就一直留在 pool，所以 RO page 從 frame cache 移出時，只要讓 PTE 失效、丟掉 frame，不必重新壓縮。RW page 則要在移出時壓縮，解壓縮回來後再釋放物件。

    10. 兩個 MMU

    第 9 節提到加速器有自己的 MMU。這一節先從零開始說明它要解決什麼問題，最後才和 CPU MMU 比較。

    先釐清一點：LZ4 規格沒有定義任何 MMU。LZ4 MMU、COT、CTLB 都是本文這個假想 SoC 的設計與名稱。實際產品可能有類似功能，但名稱和細節都不同。

    問題：壓縮後的大小每次都不同

    假設一個 4KB page 壓成 2296 bytes，要存進 pool。最直接的做法是找一段連續空間放進去，但下一個物件可能是 3200 bytes，再下一個是 26 bytes。物件反覆存入和刪除之後，空間會被切得零零碎碎，於是出現下圖上半部的情況：空間總量夠，卻放不下。

    所以本文把 pool 切成固定 512B 的 chunk，放不下一個 chunk 就再多拿一個。代價是同一個物件的片段會散落各處，因此需要一個地方記錄它們的位置。

    COT：記錄物件存在哪裡的表

    物件就是一個被壓縮的 page。COT（Compressed Object Table）是放在 DRAM 裡的一個陣列，每格 32 bytes，每個可壓縮 page 固定一格，記錄壓縮後的長度、用了幾個 chunk，以及各個 chunk 的編號。Page 目前沒有壓縮物件時，這一格的 valid 是 0。

    Handle 就是 page 在可壓縮範圍裡的編號，也是這個陣列的索引：handle = (VA - 0x7F12_2000_0000) ÷ 4096。CPU 讀到 PTE 無效的 page 時，kernel 不必另外記錄 handle，直接由 fault 的 VA 算出來，交給加速器，加速器再用它查 COT。這就是 CPU 和加速器之間的接點。例子裡的 page 在 VA 0x7F12_3456_7000，handle 是 0x1456_7000 ÷ 0x1000 = 0x14567，落在 RW 那一段。

    地址翻譯：為什麼叫 MMU

    解碼器只想循序讀取壓縮資料，它不該處理「讀完 512 bytes 後要換到哪個地址」這種事，所以只會問：物件 0x14567 的第 1100 個 byte 在哪裡？把這個連續的位置轉成實際的 PA，就是地址翻譯，所以本文稱它為 MMU：

    空的 chunk 怎麼找

    LZ4 MMU 用一個堆疊管理空的 chunk，也就是一疊可用的 chunk 編號：壓縮時輸出每滿 512B 就取走最上面的一個；物件被釋放時，再把它的編號放回去。不論 chunk 在哪裡，取用都只要一步，也不必搬移資料。

    275 MiB 的 pool 有 563,200 個 chunk，每個編號 3 bytes，完整清單約 1.6 MiB，放不進晶片裡。所以本文把堆疊分成兩段存放：

    • 最上面一段在 LZ4 MMU 的 SRAM：最多 512 個編號，共 1.5 KB。取用和放回都只動這一段，不必等 DRAM。
    • 其餘的存在 pool 裡空著的 chunk：這種 chunk 稱為 list chunk。它的前 3 bytes 是下一個 list chunk 的編號，後面放 169 個空 chunk 的編號，共 510 bytes。List chunk 一個接一個串起來，第一個的編號放在加速器的 LIST_HEAD 暫存器。
    • 「沒有下一個」用 0xFFFFFF 表示：3 bytes 有 24 bits，但 563,200 個 chunk 的編號只用到 0x000000 到 0x0897FF，所以 0x089800 以上都不是合法編號，本文取 0xFFFFFF。不能用 0，因為 chunk 0 是一個真的 chunk。最後一個 list chunk 的 next 是 0xFFFFFF；沒有任何 list chunk 時，LIST_HEAD 也是 0xFFFFFF。補充時如果讀到 0x089800 以上、又不是 0xFFFFFF 的值，代表清單壞了，加速器停止並回報錯誤。

    兩段之間什麼時候搬動：

    • 補充（refill）：SRAM 少於 64 個編號時，讀 LIST_HEAD 指的 chunk，把 169 個編號放進 SRAM，LIST_HEAD 改成它記的下一個。這個 chunk 讀完也空出來了，它自己的編號一起放進去，所以一次補 170 個。
    • 溢出（spill）：SRAM 超過 448 個時，從 SRAM 取一個編號當新的 list chunk，把原本的 LIST_HEAD 和 169 個編號寫進去，再把 LIST_HEAD 指向它。SRAM 因此少了 170 個。

    兩個門檻離得很遠：補充後最多 233 個，溢出後至少 279 個，所以不會剛補完就馬上溢出，來回搬動。一次壓縮最多用 7 個 chunk，降到 64 才補充，有足夠的餘裕等 DRAM 回應。每次搬動只是一次 512B 的 DRAM 存取，平均每取用或放回 170 次才發生一次。開機時，RO 物件已經佔用 pool 開頭的 chunk，kernel 下一個初始化指令，加速器就把其餘的 chunk 寫成 list chunk 的串列。SRAM 和 list chunk 都用完時，才回報 POOL_FULL。第 12 節最後的例子只有 24 個 chunk，整個堆疊都放得進 SRAM，所以那裡看不到 list chunk，LIST_HEAD 一直是 0xFFFFFF。

    CTLB：不要一直查 COT

    COT 在 DRAM 裡，每查一次都要等 DRAM。解碼一個物件時，每換一個 chunk 都要知道下一個編號，如果每次都查，5 個 chunk 就要多讀 5 次 DRAM。其實第一次讀到的 32 bytes 就已經包含全部編號，所以把它留在加速器內的小快取就好，這就是 CTLB。

    它和 CPU 的 TLB 目的相同，但小得多。本文的 SoC 只有一個 engine，一次解壓縮一個物件，所以 CTLB 只存 1 筆，也就是正在解壓縮的那個物件的 32-byte COT entry。換到下一個物件時，舊的那筆就被蓋掉。

    多存幾筆也不會更快。RW 物件解壓縮完就被釋放；RO 物件雖然一直保留，但要等這個 page 從 frame cache 移出、之後又被用到，才會再讀一次，中間隔很久，CTLB 早就換過別的物件。下表是連續解壓縮 3 個不同物件、每個物件 5 個 chunk 時，讀取 COT 的次數：

    CTLB 筆數讀 COT 次數原因
    0（沒有 CTLB）15每換一個 chunk 就讀一次：3 × 5
    13每個物件只在開始時讀一次
    100033 個物件都不同，存再多筆也一樣查不到

    CPU 的 TLB 不同：程式會反覆存取同一批 page，所以多存幾筆就能提高命中率。CTLB 要增加筆數，只有在硬體同時處理多個物件時才需要，例如 4 個 engine 就各要 1 筆；如果想提早載入排隊中下一個工作的 entry，也要多 1 筆。

    即使只有 1 筆，工作結束後舊資料仍留在 CTLB 裡。所以 RW 物件被釋放時，kernel 要下 INVALIDATE 指令清掉它：同一個 page 之後再被壓縮，會用同一個 handle 寫入新的 chunk 清單，CTLB 如果還留著舊的，就會讀錯 chunk。RO 物件永遠不釋放，不需要這一步。

    全部串起來

    RW page 移出（壓縮）：

    1. Kernel 由 VA 算出 handle，把 frame 的 PA 和 handle 交給加速器。
    2. 編碼器產生輸出，每滿 512B，LZ4 MMU 就從堆疊取一個 chunk 並寫入。
    3. 完成後，把長度和 chunk 編號寫進 COT 的 handle 那一格。
    4. Kernel 讓 PTE 保持無效，把 frame 還給 frame cache。

    這 4 步是摘要。下面逐步看 kernel 和加速器各做了什麼，以及 PTE、描述子、堆疊、COT entry 每一步的內容。Page 還是上面的 RW page：VA 0x7F12_3456_7000，handle 0x14567，目前在 frame 0x9A2B_4000。它的內容借用第 5 節的文字樣本，壓縮後正好 2296 bytes、670 個 sequence，和前面的例子一致；chunk 邊界落在第幾個 sequence、checksum 是多少，都是本頁的 LZ4 程式實際算出來的。堆疊裡其他 page 的 chunk 編號是示意值。

      RO page 移出：只要讓 PTE 失效，把 frame 還給 frame cache。壓縮物件從開機起就在 pool 裡，加速器完全不用參與。

      解壓縮（把 page 取回來）：

      1. CPU 讀到無效的 PTE，發生 page fault。Kernel 由 VA 算出 handle，準備一個 frame。
      2. LZ4 MMU 讀一次 COT，取得長度和 chunk 清單，並留在 CTLB。
      3. 解碼器循序要求 byte，LZ4 MMU 轉成 chunk 內的 PA。還原的資料寫到 frame。
      4. Kernel 把 PTE 改成有效，指向這個 frame。如果是 RW 物件，再下 INVALIDATE 釋放它，把 chunk 放回堆疊；RO 物件保留不動。

      同一個 page 過了一段時間又被用到。這段時間裡其他 page 解壓縮時退還了很多 chunk，堆疊的 SRAM 從 232 個變成 446 個，所以這次會看到溢出；上一個解壓縮的是 RO page 0x1A3F1，CTLB 裡留著它的 entry。

        從沒用過的 RW page（.bss、heap、stack）沒有物件，COT 的 valid 是 0。第一次用到時，kernel 直接配置一個 frame 並清成 0，不需要加速器。

        為什麼不共用 CPU MMU？

        • 大小不固定：CPU 的 page table 表達不了「2296 bytes 存在 5 個零散的 512B chunk」。把它們映射到連續 VA 也可以，但每次都要改 page table 和 shootdown，開銷太大。
        • 不能中途 fault：硬體管線停在一半等 OS 回應會很複雜，所以 kernel 先把 frame 固定、把物件準備好，LZ4 MMU 只回報結果。
        • 安全隔離：CPU 不需要直接看到 pool，也就少一條讓壞指標破壞壓縮資料的路徑。

        實際產品的 frame port 通常還會經過 IOMMU／SMMU，讓裝置看到的地址也受保護。本文省略這一層，讓兩個 MMU 的對比更清楚。

        11. Page 的狀態

        RO page 和 RW page 的狀態不一樣：RO 的壓縮物件從開機起就在 pool，只有 frame 會來來去去；RW 則和一般的記憶體壓縮相同，page 不是在 frame 裡，就是在 pool 裡，還沒用過的除外。

        同一個 page 在 DRAM 裡有幾份

        壓縮後的資料存在 pool 的 chunk 裡，COT 只是記錄長度和 chunk 編號的索引。一個 page 在 DRAM 裡可能有未壓縮的一份（在 frame）、壓縮的一份（在 pool），或兩份都有、兩份都沒有：

        RW正在使用中被移出後只在壓縮或解壓縮的過程中短暫出現還沒用過
        RO不會發生不在 frame cache 時在 frame cache 裡時，一直如此不會發生
        Pinned一直如此不會發生不會發生不會發生

        RW 壓縮時，加速器寫 chunk 的期間 frame 還留著，COMPRESS 完成後 kernel 才釋放 frame；失敗時已取的 chunk 會退還，page 只留在 frame。RW 解壓縮時，解碼器寫 frame 的期間 chunk 還在，PTE 設為有效之後 kernel 才下 INVALIDATE 釋放物件。RO 則是刻意保留壓縮副本，換來移出時只要丟掉 frame。

        同時可以有多少個「可壓縮、但現在是未壓縮」的 page：就是 frame cache 裡放了多少 page，最多 140 × 256 = 35,840 個。剛開機時是 .data 的 6,656 頁；RW 用到最多時，熱的 RO 7,680 頁加上熱的 RW 20,480 頁，共 28,160 頁，其餘 7,680 個 frame 是 margin。相對地，正在解壓縮或壓縮中的 page，同一時間只有一個，因為本文的加速器只有一個 engine；其他請求排在提交佇列裡依序處理。

        以 malloc() 為例

        C 的 malloc() 拿到的記憶體來自 heap，而 heap 在可壓縮範圍的 RW 那一段，所以它配置的記憶體可以被壓縮。下面以 p = malloc(10000) 為例，假設回傳 p = 0x7F12_2B1C_0F80。這 10000 bytes 橫跨 4 個 page，handle 是 0xB1C0 到 0xB1C3。

        剛配置：malloc() 回傳時。malloc() 是 C library 的函式，它做的事是：

        1. 在自己管理的 heap 裡找一塊夠大的空位。這塊 heap 是它先前向 kernel 要來的 VA 範圍。
        2. 空位不夠時，向 kernel 要更多 VA，例如透過 brk 或 mmap。Kernel 只記下「這段 VA 現在可以用」：PTE 仍然無效，沒有配置 frame，也不碰 COT 和加速器，DRAM 完全沒有變化。
        3. 在區塊前面寫一個小 header，例如 16 bytes，記錄大小，然後回傳 p。
        Page（handle）malloc() 回傳時的狀態
        0xB1C0Header 在這一頁（0x7F12_2B1C_0F70）。malloc() 寫 header 時就碰到了這一頁，所以它已經經歷過下面「第一次讀寫」的流程
        0xB1C1～0xB1C3還沒用過：PTE 無效，沒有 frame，COT 的 valid 是 0

        所以 malloc(10000) 不會立刻用掉 10000 bytes 的 DRAM，它只保留了 VA。

        第一次讀寫：例如寫入 p + 5000。p + 5000 = 0x7F12_2B1C_2308，在 page 0xB1C2：

        1. CPU MMU 的 TLB 查不到，walker 走 page table，發現 PTE 無效，發出 page fault。
        2. Kernel 確認這個 VA 在 heap 已配置的範圍內，所以不是程式錯誤；不在範圍內的話，程式會被終止。
        3. Kernel 算出 handle 0xB1C2，看到 COT 的 valid 是 0：這頁從沒用過，不需要加速器。
        4. 從 frame cache 拿一個空 frame。如果 frame cache 滿了，要先移出別的 page：RO 直接丟掉 frame，RW 要先壓縮。只有這一步可能用到加速器。
        5. 把整個 frame 清成 0。這一步不能省，否則程式會讀到前一個使用者留下的資料。
        6. 把 PTE 設成有效、可寫，指向這個 frame，然後從 fault 返回。
        7. CPU 重新執行剛才那條寫入指令，這次成功了。

        第一次讀取的流程幾乎一樣，讀到的值都是 0。Linux 有個最佳化：第一次只讀時，先對應到一個全系統共用、內容全是 0 的唯讀 frame，第一次寫入才真正配置 frame，所以只讀不寫的 page 不佔記憶體。之後再讀寫同一頁就不會 fault；其他 page 各自在第一次被碰到時，重複一次這個流程。

        之後：這頁變冷、frame cache 又不夠時，它會被壓縮成 RW 物件；再被用到時解壓縮回 frame，並釋放物件，也就是上面狀態圖的 RW 路徑。呼叫 free(p) 時，allocator 通常只把這塊標成可以再用，page 不會還給 kernel，已經沒用的資料仍然佔著 frame，變冷後甚至會被壓縮存進 pool。如果 allocator 透過 madvise 之類的機制告訴 kernel「這段不要了」，kernel 就能直接丟掉 frame 或釋放物件，讓這頁回到「還沒用過」的狀態。

        不能用一般 malloc() 的情況：DMA buffer 和 HRT 用的記憶體。裝置存取時不會觸發 page fault，HRT 也等不起解壓縮，所以這類記憶體要從 pinned 區配置；第 9 節 pinned 區的 22 MiB 執行期資料就是留給這類用途。另一種做法是在使用期間暫時鎖定 page，讓它不會被移出。

          流程之間的鎖

          同一時間可能有多個執行緒碰到同一個 page。第一個觸發 fault 的執行緒負責解壓縮，其他執行緒的 fault 會看到 page 正在處理，就等在鎖上。Kernel 也必須處理「正在壓縮時就有人要用」的情況：等壓縮完成後，直接走解壓縮，或取消這次換出。

            13. 延遲與容量

            這兩個計算器的預設值全部是假設，用來理解取捨，不是實測結果。第二個計算器的預設值就是第 9 節的假設量測值，請改成你自己量到的數字。

            一次壓縮 page fault 要多久

            解壓縮本身常常不是最大的成本：陷入 kernel、配置 frame、更新 page table 都要時間。所以熱 page 不該被壓縮，反覆換入換出時加速器再快也救不了。

            DRAM 要多大：從量測值算起

            算法和第 9 節相同：COT = 可壓縮 page 數 × 32 B；frame cache 至少要放得下熱的 RO 和熱的 RW；pool 至少要放得下全部 RO 物件和冷的 RW 壓縮後的大小。剩下的就是 margin，要分給 frame cache 和 pool。壓縮比要包含 512B chunk 的進位。

            14. HRT 與 QoS

            HRT 的資料由三道機制保護，少一道都不夠：

            • 配置：HRT 的程式和資料在 image 的 pinned 區，display buffer 在 carve-out。兩者都不在可壓縮範圍裡，reclaim 根本看不到它們。
            • 路徑：Display 直接經過 interconnect 到 DRAM，不經過加速器，也不查 COT。
            • 頻寬：加速器會產生大量 DRAM 流量，所以 arbiter 要給 HRT 較高優先權，並限制加速器的 burst 與速率。

            和你之前的條件有什麼不同。你之前的前提是「所有 client 都經過同一個壓縮層」。這份文件的硬體是 page 層加速器，只有在換入換出時才參與，HRT 與一般存取都不經過它。

            對照前面的比較圖，它最接近 Option C，因為都由 OS 挑冷 page，差別在這裡連讀取都要先 fault 並解壓縮；Option C 的 inline 硬體則可以直接讀。好處是不必改動 DRAM 的主要路徑，也不會有實體記憶體默默用完的問題：pool 滿了，加速器只會回報 POOL_FULL，kernel 改丟 RO page 的 frame，沒有資料遺失。哪些資料可以被壓縮，在建置時就由 image 的兩個區決定好了。

            • 編碼器：以 lz4 v1.10.0 比對 456 組資料。其中 432 組工具輸出壓縮 block，頁面程式的結果全部逐 byte 相同；另外 24 組工具改存未壓縮，因此沒有比對內容。
